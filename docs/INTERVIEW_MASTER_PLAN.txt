### Core Problem Statement (verbatim reframe)
> *"As you attach more tools to an LLM, accuracy degrades. Design a system where this is NOT a hard constraint."*

The answer: **Semantic Tool Routing + Hierarchical Agent Architecture** — treat tools like a knowledge base and retrieve them dynamically, same as you'd retrieve relevant document chunks.

## 2. The Winning Architecture

### The Core Insight (Impress Them With This)

> **Tools are to an Agentic System what Documents are to RAG.**  
> You don't stuff all 100 documents into a prompt — you retrieve the top-k relevant ones.  
> You should NOT stuff 100 tool schemas into a prompt either — you retrieve the top-k relevant tools.

### High-Level Architecture: "Dynamic Tool RAG + Hierarchical Dispatch"

```
┌──────────────────────────────────────────────────────────────────┐
│                        USER CHAT INTERFACE                        │
│                  (Multi-turn · Session Context)                   │
└───────────────────────────────┬──────────────────────────────────┘
                                │
                                ▼
┌──────────────────────────────────────────────────────────────────┐
│                    SUPERVISOR / INTENT ROUTER                     │
│  • Fast LLM (GPT-4o-mini / Gemini Flash)                         │
│  • Classifies intent → domain                                     │
│  • Maintains conversation memory (LangGraph checkpointer)         │
└──────┬──────────────────────────────────────┬────────────────────┘
       │                                       │
       ▼                                       ▼
┌─────────────────┐                 ┌──────────────────────────┐
│  TOOL RAG INDEX │                 │   DOMAIN EXPERT AGENTS   │
│                 │                 │                          │
│  All 100+ tool  │  ──top-k──►    │  Payments Agent (12 tools│
│  descriptions   │  retrieval      │  Invoicing Agent (8 tools│
│  embedded in    │                 │  Reports Agent  (10 tools│
│  vector store   │                 │  RAG Tool               │
│  (FAISS/pgvec)  │                 │  System Search Tool     │
└─────────────────┘                 └──────────────────────────┘
                                               │
                                               ▼
                                 ┌─────────────────────────┐
                                 │   TOOL EXECUTOR NODE    │
                                 │  • API calls (PayPal)   │
                                 │  • RAG retrieval        │
                                 │  • System search        │
                                 │  • Error handling       │
                                 │  • HITL gate (writes)   │
                                 └─────────────────────────┘
                                               │
                                               ▼
                                 ┌─────────────────────────┐
                                 │  RESPONSE SYNTHESIZER   │
                                 │  (Full LLM + context)   │
                                 └─────────────────────────┘
```

### The 4 Key Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| **Orchestration** | LangGraph | Stateful graph, checkpointing, HITL, conditional routing — purpose-built for agentic workflows |
| **Tool Routing** | Semantic Tool Retrieval | Embed tool descriptions, retrieve top-k per query — scales to ∞ tools |
| **Memory** | LangGraph + PostgreSQL Checkpointer | Persistent multi-turn, resume after failure |
| **Observability** | LangSmith | Native LangGraph tracing, replay failed runs, latency breakdown |

## 7. Interview Talking Points

### Q: How does your design handle 100+ tools without degrading accuracy?
> "We treat tools exactly like documents in RAG. Instead of stuffing all 100 tool schemas into the prompt, we embed tool descriptions into a vector store and retrieve only the top-5 most relevant tools per query using hybrid search — the same HNSW + BM25 + RRF pipeline from my RAG-Entreprise platform. This keeps the LLM context window focused and accuracy stays high regardless of how many total tools exist."

### Q: Why LangGraph over LangChain / CrewAI / AutoGen?
> "LangGraph is a stateful directed graph — it's the right primitive for agentic workflows. LangChain chains are stateless and can't handle branching well. CrewAI is great for multi-agent collaboration but is opinionated and overkill for a single-user chat system. AutoGen is powerful for research and code-generation agents but doesn't give you the fine-grained control over routing and HITL that financial operations demand. LangGraph gives me: persistent state via checkpointers, conditional edges for routing, native human-in-the-loop interrupts for high-stakes API calls, and first-class LangSmith observability."

### Q: How do you handle tool call failures?
> "Three layers: (1) Parameter validation before execution — if the LLM hallucinated a parameter, we catch it and ask the user to clarify before hitting the API. (2) Circuit breaker — exponential backoff on 429/500 errors, with a fallback_node that tells the user the service is temporarily unavailable. (3) State recovery — LangGraph's PostgreSQL checkpointer means if a tool hangs, we don't lose the conversation. We can resume from the last checkpoint or roll back."

### Q: How do you handle multi-turn conversations?
> "LangGraph's checkpointer persists the full graph state keyed by session_id. Each turn appends to the message history in state, so the router sees full conversation context. The system search tool can also query the audit log to answer 'what was the status of my last request?' — conversational context AND historical context."

### Q: What observability tools would you use?
> "LangSmith is the first choice — it's native to LangGraph and gives you full trace trees showing every node execution, tool call, token count, and latency. For LLM evaluation at scale, I'd add Arize Phoenix to detect hallucination, monitor retrieval quality, and run regression tests after any model upgrade. MLflow tracks the tool selection accuracy experiments as we scale from 50 to 500 tools."

### Q: How does this relate to FinTech / Capital Markets?
> "The PayPal API scenario maps directly to investment bank operations: payment tools → trade settlement, invoice tools → fee billing and invoicing, dispute tools → counterparty dispute management, analytics tools → portfolio cost reporting. Datazoic's Prism product combines CRM, BI, and AI — this agent architecture naturally extends to: a Prism user asking 'show me Q3 revenue for Morgan Stanley accounts' (analytics tool), 'draft a renewal proposal for client X' (RAG tool over pitch templates), or 'what's the status of that wire transfer?' (system search tool over audit logs)."
